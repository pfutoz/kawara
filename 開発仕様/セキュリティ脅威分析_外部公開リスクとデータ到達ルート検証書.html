外部公開時におけるデータ突破ルート検証

院内かわら版（Cloudflare Tunnel連携）の外部公開状態において、万一Webアプリケーション境界が突破された場合に「職員個人情報」および「患者診療データ」まで到達し得る具体的ルートの技術的検証と緊急対策処方箋

調査日: 2026年10月15日
対象ホスト: 192.168.1.16（院内本番サーバー）
対象ドメイン: kawara.ono.or.jp
評価ランク: 構造的重大リスク確認（要多層防御）
← 開発指針・仕様書ポータルに戻る
SECTION 01

現状のシステムアーキテクチャと危険因子（アタックサーフェス）

調査によって特定された、院内サーバー（192.168.1.16）の内部構造および危険因子は以下の通りです。

🌐 外部トンネル境界
  • 経路: Cloudflare Zero Trust Tunnel (cloudflared)
  • 公開ドメイン: https://kawara.ono.or.jp
  • 直通先: 院内LAN最深部 192.168.1.16:80（リバースプロキシを介さず直結）
⚙️ Webサーバー実行権限
  • Webサーバー: Apache 2.4.66 + PHP 8.5.5 (Win64)
  • 実行アカウント: jmt\owner（管理者ローカルユーザー）
  • 影響: PHPコード実行を奪取された場合、サーバーOSの完全支配が可能
🗄️ PostgreSQLデータベース同居構造
  • ホスト: localhost:5432
  • 接続ユーザー: postgres（全権スーパーユーザー）
  • 同居DB: kawara, meibo, monshin, old_pacient, endoscope
🔌 院内ネットワークセグメント
  • 所属IP: 192.168.1.111 / 192.168.1.16 (同一 /24)
  • 同居機器: 電子カルテ端末、医事会計レセコン、院内NAS、複合機
  • セグメンテーション: DMZ等の論理的分離なし（フラットLAN）
// includes/db.php に記述されていた実際のDB接続定義（全権ユーザー接続） if (!defined('DB_HOST')) define('DB_HOST', 'localhost'); if (!defined('DB_USER')) define('DB_USER', 'postgres'); // ← スーパーユーザー if (!defined('DB_PASS')) define('DB_PASS', 'postgres'); // ※ PostgreSQL内には kawara 以外に monshin（問診）、old_pacient（過去カルテ）が同居
ROUTE 01

【検証ルート1】職員個人情報まで到達する侵入シナリオ

悪意ある攻撃者がインターネット側からCloudflare経由で侵入を試み、全職員のプライベート個人情報（氏名、生年月日、住所、電話番号、LINE ID、パスワード等）を奪取するまでの具体的ステップです。

1
外部公開エンドポイントの探索と脆弱性の突合 境界突破フェーズ

攻撃者は https://kawara.ono.or.jp に対し自動スキャナーを実行。認証前でもアクセス可能なAPI（api/device_auth.php や login.php、画像アップロード機能等）を探索します。

# 攻撃手法例: SQLインジェクションの試行 POST /kawara/api/device_auth.php HTTP/1.1 Host: kawara.ono.or.jp Content-Type: application/x-www-form-urlencoded action=verify&device_token=' UNION SELECT 1, staff_id, staff_name, password_hash FROM staff--

※ 現行コードはPDOプレペアードステートメントを使用していますが、将来的なコード追加や第三者改修で1箇所でも動的SQL文字列結合（$sql = "... WHERE id = " . $_GET['id']）が生じた瞬間、この突破口が開かれます。

2
かわら版DB（kawara.staff）からの職員基本台帳窃取 内部データ流出

SQL実行能力を獲得した攻撃者は、直ちに kawara.staff テーブルへ問い合わせを実行します。

  • 流出するデータ項目: 職員ID、氏名、役職、所属部署、ログインID、パスワードハッシュ、LINE User ID（line_user_id）、端末自動ログイン用Cookieトークン。
  • 二次被害: 事務長・管理者アカウントへの不正ログイン、職員個人LINEへの標的型スピアフィッシング、安否確認システムの虚偽発令。
3
同一DBインスタンス内の「meibo（名簿）」データベースへの横移動 致命的プライバシー侵害

ここが最大の危険箇所です。PostgreSQLの接続権限がスーパーユーザー（postgres）であるため、データベース間のアクセス制御が機能していません。攻撃者はPostgreSQLの標準拡張機能（dblink）またはPHPの新規接続コードを利用して、meibo データベースを直接参照します。

-- dblink拡張を用いた別データベースの直接盗み出し（postgres権限なら実行可能） SELECT * FROM dblink('dbname=meibo user=postgres password=postgres', 'SELECT staff_name, home_address, tel_number, family_contact FROM employee_records') AS t(name text, addr text, tel text, family text);

結果: 病院全職員の現住所、個人携帯番号、家族情報、給与振込先等の機微情報が完全に外部流出します。

ROUTE 02

【検証ルート2】患者診療・問診・過去カルテデータまで到達するルート

医療機関として最も避けるべき最悪のシナリオ（患者個人情報および診療履歴の漏洩・改ざん、電子カルテ端末のランサムウェア暗号化）への到達ルートです。

1
Webシェル（バックドアスクリプト）の設置（RCE） OSコマンド実行権の奪取

SQLインジェクションの COPY TO / pg_read_file コマンド、あるいは画像ファイルアップロード機能の拡張子検証漏れ（Polyglotファイル攻撃）等を悪用し、c:\Apache24\htdocs\kawara\uploads\shell.php 等のWebシェルを配置します。

# 攻撃者が外部から実行するリクエスト例 GET /kawara/uploads/shell.php?cmd=whoami HTTP/1.1 Host: kawara.ono.or.jp # サーバーからの応答 HTTP/1.1 200 OK jmt\owner ← Windowsの管理者権限で実行されていることが判明
2
同居する患者医療データベースのダンプ（即座の流出） 医療法・個人情報保護法違反

攻撃者はOSコマンドまたはPHP直接実行により、サーバー上のPostgreSQLから全患者データベースを即座に外部へ吸い出します。

# 攻撃者が実行するバックアップダンプコマンド pg_dump.exe -U postgres monshin > c:\Apache24\htdocs\kawara\uploads\patients_monshin.sql pg_dump.exe -U postgres old_pacient > c:\Apache24\htdocs\kawara\uploads\old_pacient.sql pg_dump.exe -U postgres endoscope > c:\Apache24\htdocs\kawara\uploads\endoscope.sql
💥 実際に到達・流出する患者データ:
  • monshin DB: 患者氏名、フリガナ、生年月日、電話番号、来院目的、主訴（症状）、既往歴、服薬歴、アレルギー情報。
  • old_pacient / ono_oldpatient DB: 過去患者基本台帳、カルテ病名、受診履歴、患者ID。
  • endoscope DB: 内視鏡検査所見、検査日、生検・診断結果。
3
院内LAN（192.168.1.0/24）への横移動（ラテラルムーブメント） 病院機能停止リスク

Apacheがローカル管理者（jmt\owner）権限で稼働しているため、攻撃者はサーバーを「踏み台（Pivot）」として、病院内LAN全体へ攻撃を展開します。

# PowerShellを用いた院内端末の探索スキャン 1..254 | % { Test-NetConnection -Port 445 -ComputerName "192.168.1.$_" -WarningAction SilentlyContinue }
  • 電子カルテ端末・レセコンへの侵入: SMB（445番ポート）やRDP（3389番ポート）を狙ったブルートフォース攻撃や脆弱性悪用。
  • ランサムウェアの配布: 院内共有NASや各部署端末のファイルを一斉暗号化し、身代金を要求（近年の医療機関サイバー攻撃の典型パターン）。

DEFENSE

具体的かつ現実的な多層防御策（処方箋）

🛡️ 防壁1: 事務長キルスイッチの運用（実装完了・即効性100%）

「普段（夜間・平時）は完全遮断（OFF）にしておき、災害時・緊急時のみONにする」 という運用ルールを徹底します。外部から攻撃者が侵入を試みる時間窓（Window of Exposure）を年間の0.1%以下に圧縮するため、常時公開に比べてリスクは99.9%低減されます。

🔒 防壁2: PostgreSQL接続アカウントの厳格分離（最小特権の原則）

db.php の接続ユーザーを全権 postgres から、かわら版専用ユーザー kawara_user に切り替えます。

-- かわら版専用ユーザーの作成と権限の完全隔離（患者DB・名簿DBへのアクセスを遮断） CREATE USER kawara_user WITH PASSWORD 'StrongPasswordHere'; GRANT CONNECT ON DATABASE kawara TO kawara_user; -- monshin, old_pacient, meibo への接続権限を一切与えない（REVOKE CONNECT） REVOKE CONNECT ON DATABASE monshin FROM PUBLIC, kawara_user; REVOKE CONNECT ON DATABASE old_pacient FROM PUBLIC, kawara_user; REVOKE CONNECT ON DATABASE meibo FROM PUBLIC, kawara_user;

※ これにより、万一かわら版側でSQLインジェクションが起きても、患者DBや名簿DBへのアクセスはPostgreSQLエンジンにより物理的に拒絶されます。

☁️ 防壁3: Cloudflare Zero Trust による境界保護

Cloudflareダッシュボード側で「WAF（Managed Ruleset - OWASP Top 10 / SQLi検知）」を有効化し、海外IPからのアクセス遮断（日本国内限定Geo-blocking）および、職員端末へのCloudflare Access（PINコード認証等）を重畳します。

🚀 将来構想: クラウドDMZ分離（院内LANへの直通トンネル撤廃）

外部公開が必要な「安否確認」「医師予定表」データのみを、院内サーバーからクラウド（AWS/Supabase等）へ一方向（Outbound）で定期同期させ、職員のスマホはクラウド側のみを参照するアーキテクチャに進化させます。これにより、院内LANへのインバウンド接続（トンネル）が不要となり、院内データ突破リスクは論理的にゼロになります。
